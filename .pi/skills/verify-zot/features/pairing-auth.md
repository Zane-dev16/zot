# Pairing and devices

What: Bearer token comes from pairing. `POST /api/v1/pair/start` returns `{code, expiresAt}` (rate-limited); `POST /api/v1/pair/confirm` with code returns `{token, device}` 201 (public, no token). All other `/api/v1` routes need `Authorization: Bearer $TOKEN` or 401.
Reach: the Pairing view (`#pairStart` → `#pairCode` → `#pairConfirm`, states named on `#pairStatus[data-kind]`), the manual `#token`/`#saveToken` fallback, or curl pair/start → pair/confirm; iOS sets Base URL to host:port, enters 6-digit code within 5 min. One pending code per daemon: a second pair/start replaces it, and a browser confirm after a phone's start answers `no-pending`/`mismatch` rather than pretending. Pairing POSTs are rate-limited to 5 per 60 s, shared by pair/start and pair/confirm; over budget answers 429 `rate limited`.
Drive: pair/start (kind must be `browser` or `ios`) → pair/confirm → save token → `GET /api/v1/devices` lists sessions → `DELETE /api/v1/devices/:id` revokes. Negative: `GET /api/v1/runs` without token → 401 JSON error. The token lives in `localStorage["zot.token"]` and the browser sends it as the stream's `?token=` query; the console never puts it in the page URL or hash. `#signOut` clears token + replay cursor client-side (no revoke endpoint in the allowed set).
Prove: confirm returns 201 with token; authed call 200; unauthed 401; revoked device cannot call.
